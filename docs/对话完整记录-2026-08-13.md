## 项目里 ReAct 循环实际存在的地方

**1. AgenticNode 内部(真正的 ReAct 循环)** — `gen_sql` 就是这一类:

- `GenSQLAgenticNode(AgenticNode)`,`gen_sql_agentic_node.py:78` 设置 `max_turns = 50`
- 核心循环在 `agentic_node.py:3298` 调 `self.model.generate_with_tools_stream(..., max_turns=effective_max_turns)`,这是 OpenAI Agents SDK 的 agent loop:LLM 思考 → 发起 tool call → 工具执行 → 结果喂回 → 继续,直到模型不再调工具或耗尽 50 轮
- gen_sql 挂载了 `DBFuncTool`(`gen_sql_agentic_node.py:203`),即查表、看 schema、执行 SQL 验证、context search 等工具,所以它能在节点内部"写 SQL → 跑一下 → 看到报错 → 自己改",是标准 ReAct
- 外层还有一层 retry policy 循环:`agentic_node.py:3152` 按 `max_attempts` 多次重跑 `_stream_once`
- 新架构里所有 `AgenticNode` 子类(chat、explore、gen_report、gen_metrics…)都走同一套循环

**2. 工作流层的"反思循环"(传统架构的外层 ReAct)**:

- `reflect` 节点执行完会按 strategy 动态往 workflow 里插入新节点序列(schema_linking → gen_sql → execute_sql → reflect),插到当前位置(`reflect_node.py:128` 的 `_execute_strategy`)
- 由 `MAX_REFLECTION_ROUNDS`(默认 3,`reflect_node.py:111`)封顶,超限就转 `reason_sql` 节点收尾
- 所以传统流水线本质是:**每次 reflect 不合格 → 整个子流水线再来一轮**,循环在 workflow 层,不在单个节点内部

**3. ReasonSQLNode(反射超限后的 REASONING 节点)**:通过 `reasoning_sql_with_mcp` + `tool_config={"max_turns": ...}`(`reason_sql_node.py:179`)调用 `generate_with_tools`,带 DB 工具的 tool-calling 循环,也算一个 ReAct 式节点。

## 一句话总结

- 你说的这 5 个节点里,只有 `gen_sql` 内部有 ReAct 循环(且是完整的 SDK agent loop,最多 50 轮)
- 传统流水线的"多轮迭代"来自 **reflect 节点动态改图** 的工作流级循环(默认最多 3 轮反思)
- 项目里 ReAct 式循环的真正主体是**新架构的 AgenticNode**(chat/gen_sql/explore 等),一个节点就是一个带工具的 agent,传统单次调用节点正在被它取代(`workflow.yml` 里的 `chat_agentic` / `gen_sql_agentic` 流水线)

### Claude

## 先简单解释 ReAct 循环

ReAct(Reasoning + Acting)是让 LLM 通过"边想边做"来完成任务的模式,一轮循环是:

```
Thought(思考) → Action(调用工具) → Observation(观察工具结果) → 再思考 → … 直到任务完成或轮数上限
```

关键点:**LLM 自己决定每步调用哪个工具**,而不是宿主程序预先写好调用序列。所以"写 SQL → 执行 → 看到报错 → 自己改"这类自我纠错行为,就来自这个循环。循环通常有 `max_turns` 封顶,防止无限跑下去。

## AgenticNode 的循环在哪一层实现

代码分三层,真正的 `while` 循环**不在 datus 自己写的代码里**,而在 OpenAI Agents SDK 里:

```
① AgenticNode 层(编排)        datus/agent/node/agentic_node.py
   execute_stream() 模板方法 ──► _stream_once()          :3298
                                   调用 model.generate_with_tools_stream(..., max_turns=50)
   ↑ 这层自己只有一个外层循环:retry policy 的 max_attempts (:3152),不是 ReAct 循环

② 模型接口层                   datus/models/base.py:185
   LLMBaseModel.generate_with_tools_stream() —— 抽象契约,只定义参数(max_turns/tools/session/hooks)

③ 具体模型实现层(循环真正在这里)
   ├─ OpenAI 兼容模型:openai_compatible.py:1311
   │    构建 SDK Agent → Runner.run_streamed(agent, max_turns=...)
   │    └─ 真正循环在 openai-agents SDK 的 Runner(agents/run.py)里:
   │       LLM 调用 → 解析 tool calls → 执行工具(经 hooks)→ 结果写回会话 → 再调 LLM → …
   │       直到模型不再返回 tool call、或轮数达到 max_turns(超限抛 MODEMAX_TURNS_EXCEEDED,:1197)
   ├─ Claude 模型:claude_model.py:1797(自己的实现)
   └─ Codex 模型:codex_model.py:517(自己的实现)
```

所以分工是:

- **datus 层**只负责"编排一次运行":准备好 tools / session / 权限 hooks / `max_turns`(= gen_sql 默认 50,`gen_sql_agentic_node.py:78`),然后调用模型层的流式接口
- **SDK 层**(OpenAI Agents SDK 的 `Runner`)负责反复执行 Thought→Action→Observation 的 while 循环,datus 通过 `max_turns` 和 `hooks`(权限检查、token 统计、compact 触发都挂在 hook 上)去影响和观察这个循环,而不是自己写这个循环

这也是为什么 `AgenticNode` 里你看不到显式的 tool-call while 循环——它被抽象进 SDK 了;datus 自己显式写的循环只有 retry-policy 那层(一次运行失败/不合格再整体重跑)和工作流层的反射循环。

## 先排除法(为什么不是其他的)

| 候选 | 一票否决的理由 |
|---|---|
| LangGraph / LangChain | 自带图/checkpoint 抽象,和 datus 自己的 Workflow/Node DAG(`workflow.yml`、动态插节点)正面冲突;依赖面大、对 prompt 和流式输出控制力弱。datus 需要的是"给我一个循环",不是"给我一个框架" |
| Temporal / Inngest | **类别不同**:持久化分布式工作流引擎,要 Temporal server / Inngest 云。datus 是本地 CLI/TUI 工具,零基础设施要求,一票否决 |
| Vercel AI SDK | 纯 TS/JS,项目是 Python 3.12+ |
| CrewAI | 角色式多智能体框架,Crew/Agent/Task 抽象和 datus 的 per-node 模板 + 子代理模型不匹配;反而多一层控制权损失 |
| Google ADK | Gemini 生态优先,datus 必须 provider 中立(OpenAI/Claude/Gemini/Ollama/自建端点都要支持) |
| LlamaIndex | RAG 框架,agent loop 是副业;datus 已有自己的 LanceDB RAG 栈 |
| Deep Agents SDK | 2025 年底才发布,部分功能依赖 LangChain 平台 API key,生态不成熟 |
| Claude Agent SDK | Anthropic 独占,没法做多 provider 产品(虽然 datus 单独为 Claude 写了原生循环,说明它并不迷信某一个 SDK) |

## 正选理由:SDK 恰好补上 datus 最需要的几块

1. **薄循环,不侵入架构**。SDK 只有 Agent + Runner + tools 三件套,`Runner.run_streamed(agent, max_turns=...)` 就是上一轮说的 ReAct 循环。datus 的节点/工作流/提示词体系完全保留,SDK 被压在 `LLMBaseModel` 接口下面当发动机——`docs/design/03-技术方案.md` 里管它叫"SDK 桥接"。

2. **Provider 中立,和 LiteLLM 天然契合**。SDK 接受任何 OpenAI 兼容端点,而 datus 的 `litellm_adapter.py` 把所有 provider 统一成 OpenAI 兼容协议(`pyproject.toml:44` 直接装 `openai-agents[litellm]`)。Claude/Gemini/Ollama 全走这条路,一个循环引擎覆盖绝大多数 provider。

3. **流式输出是刚需**。datus 的 TUI/CLI 要实时渲染 ActionHistory(思考、工具调用、结果逐条刷屏),`run_streamed` 的事件流正好映射成这套 action 流。LangChain/CrewAI 在这方面的控制粒度都不如它直接。

4. **Hook 生命周期成了基础设施的挂载点**。SDK 的 `on_tool_start`/`on_llm_end` 等 hooks 被 datus 用来挂:权限检查(`PermissionHooks`)、token 统计(`TokenUsageHook`)、自动 compact(`CompactHook`)、OpenInference 追踪插桩(`docs/develop/observability.md` 明确写 SDK span 并入 datus trace tree)。换一个框架,这一整套都要重写挂载方式。

5. **会话管理直接复用**。`AdvancedSQLiteSession`(SDK 自带)就是 `AgenticNode` 的持久化会话(`agentic_node.py:23`),多轮对话/resume 免了自己造轮子。

6. **MCP 支持开箱即用**。`MCPServerStdio` 直接来自 SDK(`agentic_node.py:24`)。

## 一句话总结

datus 需要的不是"多智能体框架"或"工作流引擎",而是一个**薄的、provider 无关的、流式友好的 LLM 工具调用循环**,并且要求自己保留对节点编排、提示词、权限、观测的全部控制权。OpenAI Agents SDK 是所有候选项里唯一满足"薄循环 + 多 provider + 强流式 + hook 可插拔"的 Python 方案,而且它是唯一可以垫在自研抽象(`LLMBaseModel`)底下、随时替换的那一个——这点从 Claude/Codex 各自实现循环就能看出来,选型没有锁死。

## 关键区分:循环引擎 vs 编排框架

- **OpenAI Agents SDK**:它卖的是一个**执行器**(agent loop)。边界是一个函数调用:`Runner.run_streamed(agent, tools, max_turns)`。你给它工具和配置,它跑循环,通过事件流和 hooks 把过程交还给你。它对你的编排结构**没有任何意见**。
- **LangGraph**:它卖的是一个**编排框架全家桶**——StateGraph、State/reducer、checkpointer、编译、interrupt。它不是"给你一个循环",而是"把你的编排重写成我的图模型"。

问题的核心是:**datus 已经有一套自己写的编排层了**,它缺的只是执行器。

## datus 已有的编排层(全部自己写的)

1. `datus/agent/workflow.py` — Workflow 类,节点列表 + 依赖,`add_node(node, position)` 支持**运行中在任意位置插节点**
2. `datus/agent/workflow.yml` — 流水线用 YAML 声明(reflection / fixed / metric_to_sql …)
3. **运行中动态改图**:reflect 节点会根据反思策略,在当前执行位置**现场插入**一条 `schema_linking → gen_sql → execute_sql → reflect` 子流水线(`reflect_node.py:163`),跑完再插,最多 3 轮。这是 datus 的核心机制(自我纠错)
4. 每个节点有自己的生命周期:`setup_input` → `execute` → `update_context`(把结果写回 workflow context)

如果当初选 LangGraph,你有两条路,都不好走:

- **路线 A:把编排层全部迁到 LangGraph**。上面这套(尤其是"运行中按策略插节点"和"每节点写回共享 context")要翻译成 LangGraph 的词汇表:State 定义、conditional edges、`Command`/`Send` 动态路由。LangGraph 的图是编译式的,运行中在当前位置插一个 4 节点子序列,这种"列表式工作流"的改法在它那里是别扭的(要用边条件 + 状态机绕)。等于把能跑的东西重写一遍,换来的是什么?checkpoint 持久化——而 datus 已经有自己的 session/resume 机制了。
- **路线 B:保留 datus 编排层,只用 LangGraph 当节点内的 agent loop**。技术上可行(用它的 `create_react_agent`),但你为了一个循环,引入了整个 LangChain 依赖树(版本抖动、抽象厚度),而它给不了 SDK 没有的东西,反而流式事件粒度、provider 中立性(Claude 要走原生循环)还不如直接用 SDK。

## 所以"控制权"的准确含义

不是"拒绝用框架编排",而是:

1. **编排层已经是自研资产,而且它长在用户可见的接口上**(`workflow.yml`、`Node.new_instance()` 扩展点、CLAUDE.md 里"New Node"就是扩展指南)。换成 LangGraph,这个扩展面就变成 LangGraph 的扩展面了。
2. **datus 要的是薄循环,不是第二个编排器**。SDK 的边界是一个函数调用,不合意随时可以在 `LLMBaseModel` 下面换掉(Claude/Codex 已经各自实现了循环,证明这个缝是活的)。LangGraph 的边界是整个框架,进来容易出去难。

## 坦白说代价是什么

选 SDK 不是没有代价:LangGraph 白送的 **checkpoint 持久化、中断恢复、状态版本管理**,datus 全要自己造——你在这个代码库里看到的 session 管理、plan mode 状态持久化、compact/resume 那一大坨(光 `agentic_node.py` 就 4200 行),相当一部分是在手写 LangGraph 免费给的那层东西。所以这个选择本质是:**用"自己维护状态层"的成本,换"编排层和依赖边界完全在自己手里"的自由**。对一个要长期支持 CLI/TUI/API/多租户形态、并且编排逻辑是核心差异化的产品来说,这个交易是划算的;如果你只想要一个能跑的多智能体 demo,LangGraph 可能反而更快。

## 第 5 轮

### 用户

为什么项目里还同时保留传统 workflow 和 AgenticNode 两套体系?

### Claude

查了 git 历史,两套体系的来源和边界很清楚:

- `workflow.yml`(传统流水线)出现在 **Initial commit** `eea792ec`
- `AgenticNode` 是后面 **PR #102**(`ce480bba`,ChatAgenticNode)才引入的

所以这不是"设计成两套",而是**项目起家于传统 workflow,后来加了一套新的,旧的没删**。具体原因有四个:

## 1. 服务的场景不同,需求天然冲突

**传统 Workflow 的消费者是评测,不是聊天**(证据:`datus/multi_round_benchmark.py` 的默认参数就是 `--workflow reflection`):

- 固定节点序列 = **可复现、可对比**的评测基线(每次跑一模一样的 schema_linking → gen_sql → execute_sql → reflect → output,每节点还能单独配模型)
- `MAX_REFLECTION_ROUNDS` 精确控制反思轮数,方便消融实验
- checkpoint/恢复(`Workflow.load(config.load_cp)`,workflow_runner.py:60)、成本统计——都是 benchmark 刚需

**AgenticNode 的消费者是交互产品**:API chat(`api/services/chat_service.py:183`)、REPL、TUI。需要的是多轮会话、权限、skills、subagent、流式渲染——这些能力传统节点一个都没有,而且也不该有(评测不需要人机交互)。

## 2. 结构差异大,合并 = 重写评测层

- 传统节点:同步 `execute()`、单次调用、通过 `workflow.context` 写回结果
- AgenticNode:异步流式、session 持久化、SDK 工具循环、interactive 状态机

把 reflection 流水线改写成 agentic 版本,等于重新验证一套 NL2SQL 基线——收益是"少维护一套代码",代价是评测结果漂移 + 大改面。对一个靠 benchmark 数据说话的项目,这个交易不划算。

## 3. 其实不是完全隔离的——正在收敛

`workflow.yml` 里已经出现混合计划:

```yaml
gen_sql_agentic: [gen_sql, execute_sql, output]   # agentic 节点 + 传统节点混排
```

`Node.new_instance()` 也能直接造出 `ChatAgenticNode`/`GenSQLAgenticNode`(execution_mode="workflow",node.py:112-136)。也就是说:**传统 Workflow 正在从"流水线实现"退化为"容器"**——agentic 节点可以作为它的一个节点跑,后面接 execute_sql/output 收尾。

## 4. 新功能只加在 AgenticNode 侧,传统侧冻结

权限、skills、plan mode、compact、MCP、subagent——这些年的所有新能力都在 `AgenticNode` 基类上(那个 4200 行的文件)。传统节点只做 bugfix,不再进新功能。这意味着事实上的迁移方向是明确的:**agentic 吃掉产品侧,传统 workflow 留守评测侧**。

## 一句话总结

两套并存 = 历史路径 + 场景隔离:传统 Workflow 是项目起家时的**评测引擎**(需要确定性、可控反思轮数、checkpoint),AgenticNode 是后来长出来的**产品引擎**(需要交互、会话、工具自由循环)。它俩在技术上能互通(混合 workflow),业务上也各有活干(benchmark vs chat),删掉任何一个当前都没有净收益——所以并存是**理性的技术债**,而不是混乱。

汇总了 `datus/` 里对 `agents` 包的全部导入和调用点,按能力分 9 类:
