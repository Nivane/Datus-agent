## Q1：结果复核 / 评估 / eval / check 是怎么做的？能提升准确率吗？

**问**：项目中的结果复核，或者说 评估/评测或者说 eval 或者说 check，是怎么做的，这样可以提升准确率吧

**答**：

项目里的"结果复核/评估"是**六层嵌套体系**，覆盖从"SQL 生成时"到"交付物落地后"再到"离线度量"全链路：

### 第 0 层：生成即校验（确定性、无 LLM）

- **语法/方言/语句分类**：SQLGlot 解析（`sql_utils.py` `parse_sql_statement_kind`），失败即进 `fix` 节点重写
- **EXPLAIN 行数守卫**（`tools/sql_guard.py`）：执行前跑 EXPLAIN 估算返回行数，超 5000 万拒绝并给改写建议
- 这一层拦截**必然错误**，成本最低、收益最确定

### 第 1 层：反思循环（工作流内 LLM 评估）⭐ 核心

默认 `reflection` 工作流的 `reflect` 节点（`agent/node/reflect_node.py` + `agent/reflect.py`）：

- `evaluate_with_model`：LLM 用 evaluation 模板（1.0/2.0/2.1）评估"任务描述 + 生成 SQL + 执行结果（采样行/错误/行数）"，输出 classification
- 策略白名单：`STRATEGY_LIST`（SUCCESS/DOC_SEARCH/SIMPLE_REGENERATE/SCHEMA_LINKING/REASONING/COLUMN_EXPLORATION/UNKNOWN）——LLM 输出不受控时按 UNKNOWN 兜底（`evaluate.py:52-55`）
- 策略执行（`reflect_node.py`）：
  - SUCCESS → 前进到 output
  - SIMPLE_REGENERATE → LLM 自带修正后 SQL 直接 append 重执行
  - DOC_SEARCH / SCHEMA_LINKING / REASONING / COLUMN_EXPLORATION → 从 `reflection_nodes.<strategy>` 配置取节点序列**插入当前工作流**（`reflect_{round}_{strategy}`）
- **轮次上限**：`MAX_REFLECTION_ROUNDS` 默认 3；到上限强制走 REASONING，超限退出——防"反思死循环烧 token"
- **防串线检查**：只有"评估的 SQL == 最后一条 SQLContext"时策略才生效（`reflect_node.py:29-45`）
- **反思节点可配置**：`reflection_nodes.<strategy>` 可插拔

### 第 2 层：输出复核（LLM，针对"答没答对题"）

`prompts/output_checking.py` `gen_prompt`：把**用户原问题 + schema + SQL + 执行结果（截断 500 字符）+ 指标 + 外部知识**一起给 LLM，检查"SQL 输出是否真正回答了用户的问题"。

### 第 3 层：交付物校验（ValidationHook，确定性 + LLM 技能双轨）

针对产生交付物的 Subagent（建表/迁移/仪表盘/调度），`validation/hook.py` 的 `ValidationHook(AgentHooks)` 在变更性工具调用后与 agent 结束时触发：

- **Layer A（确定性不变量，无条件执行）**：`builtin_checks.py` —— TableTarget→describe_table 非空、TransferTarget→行数对账、Dashboard/Chart/Dataset→BI 工具存在性、SchedulerJob→作业存在+状态
- **Layer B（LLM 校验技能，可开关）**：`skill_validators_enabled` 控制，跑校验类技能（table-validation、bi-validation、scheduler-validation 等）
- 阻塞失败记入 `final_report`，节点流结束后**驱动重试循环**；每次 run 前 `reset_session()` 防跨 run 污染

### 第 4 层：离线评测框架（准确率的"尺子"）

- 内置数据集：**BIRD-DEV、Spider2（多库）、Semantic Layer**，`datus-agent benchmark` / `datus-agent eval`
- 失败分类：`Passed / No SQL / Empty Result / Failed(Table Mismatch / Row Count Mismatch / Column Value Mismatch)`——分类直接告诉你**该优化哪一层**
- `multi_round_benchmark.py` 多轮对比，度量"上下文演化是否真的提升了准确率"

### 第 5 层：反馈闭环（在线学习）

- `feedback` 节点 + `/feedback` + `POST /chat/feedback` + `success-stories` 采集用户反馈
- 成功查询沉淀为 **SQL Summary**，下一轮同类问题直接检索命中

### 能提升准确率吗？

| 层 | 拦截的错误类型 | 提升方式 |
|---|---|---|
| 0 确定性校验 | 语法错/超量结果 | 必然有效，零幻觉风险 |
| 1 反思循环 | 执行失败/结果可疑 | 带错误信息定向重试（`reflection` 是默认工作流的原因） |
| 2 输出复核 | 答非所问 | 对题性把关 |
| 3 交付物校验 | 产物不存在/对不上账 | 确定性兜底 + LLM 技能双保险 |
| 4 评测框架 | 定位问题 | 不直接提升，但告诉你往哪优化、验证有没有提升 |
| 5 反馈闭环 | 反复犯的同类错 | 知识沉淀，长期收益 |

**两个诚实的局限**：

1. 第 1/2 层是 **LLM 自评**——评估者与被评估者同一模型，存在自我确认偏误；用 `classification` 白名单 + 轮次上限缓解，但无法根除
2. 评估失败有兜底：`evaluate_with_model` 异常时返回 `strategy="UNKNOWN"` 继续流程（`evaluate.py:63-69`）——评估挂掉不拖死工作流，但放弃该轮纠错机会

设计细节：第 1 层只评估**最后一条 SQLContext**（`reflect_node.py:78` 有 `# TODO: use all the sql_contexts` 注释）——不看完整推理历史，是已知演进空间。

## Q2：每个拥有 agent 的人都必须初始化 KB 吗？公司内部会不会重复建设？

**问**：每个拥有这个 agent 的人都必须要最开始初始化 kb吗？那一个公司内部不是会溶于（重复建设）

**答**：

**不需要每个人重复初始化**。项目把"知识内容"和"向量索引"分成两层，只有索引是本地建的，而索引可以随时从共享内容重建。

### 关键：KB 是两层结构

| 层 | 存什么 | 存哪里 | 是否随 git |
|---|---|---|---|
| **内容层** | 语义模型、指标、Reference SQL、SQL Summary（YAML 源文件） | `{project_root}/subject/` | ✅ 随仓库版本管理 |
| **索引层** | LanceDB 向量 + Tantivy 全文索引 | `~/.datus/data/{project}/datus_db/` | ❌ 本机构建 |

- **内容层是智力投入**：指标口径、值得沉淀的 SQL——一次构建、git 共享、全公司复用
- **索引层是机械动作**：内容跑一遍 FastEmbed 嵌入（本地 CPU 可跑，默认 all-MiniLM-L6-v2）。新同事 `git clone` 后跑 `/build-kb` 或 `/bootstrap`，几分钟重建索引，**不需要重新写任何知识**
- `project_name` 由仓库根目录派生：同一个 repo → 同一个项目分片 → 大家的索引指向同一套内容

### 公司内部三种协同方式

1. **单仓库模式（推荐）**：全公司共享 repo，`subject/` 由数据工程师/管道维护（`gen_semantic_model`、`gen_sql_summary` 产出 → PR 合入）。分析师 clone 后各自 `/build-kb` 建索引，`./.datus/config.yml` 配置也随仓库
2. **服务端形态（零重复）**：部署 `datus-api` / `datus-mcp`，多进程**共享同一数据目录**（DRD-02 §4.1 形态 B）——KB 全公司只有一份
3. **混合**：工程师本地 CLI 探索（探索期的"错知识"不污染共享库），成熟后 PR 入仓库，服务端跑生产

### 代价与注意点（tradeoff）

- 索引不随 git 是有意的：二进制大、绑定嵌入模型版本
- 嵌入模型一致性：`check_snapshot` 先本地后下载固定模型快照
- **真正的重复建设风险**：公司**没人维护 `subject/`** 时，每个人各自裸跑 bootstrap 才是重复劳动——语义资产要当"公共资产管道"维护（`/bootstrap-bi` 可把存量 BI 资产批量转入）
- 目前没有"索引增量推送/多机同步"机制——本地重建 + 服务端共享是设计内的两条路径；跨机共享索引是明确演进方向

**一句话：知识写一次、随仓库流动；索引人人自建、分钟级重建；要彻底零重复，上服务端形态。**

## Q3：Context 全放进一个 DB，会不会越来越大、越来越旧？

**问**（引文 + 提问）：

> Q：现在也有一些 Context DB 的思路，把 Project、Repo、业务知识和其他上下文统一放进一个中心化存储。但数据越来越多以后，一方面模型 Context 太大会变笨，另一方面知识本身也会过期，甚至互相冲突。你们怎么处理？
>
> A：我其实不太赞成一开始就做一个特别大的统一 Context DB。公司有几万张表，理论上可以全部放进去再做 GraphRAG，但工程复杂度很高，也不一定值得。我们更倾向于按 Project 或业务域组织 Context……第二个关键是 Context 要跟开发过程结合。工程师做新的 SQL、指标和 Dashboard 时，就在同一个 Project 里面把知识更新掉……所以我们更倾向于 Bottom-up，让负责这个业务的工程师在实际开发和使用中把 Context 慢慢维护准确。

**问**：这里说的"工程师做新的 SQL、指标和 Dashboard 时，就在同一个 Project 里面把知识更新掉。"对现在的 Datus Agent 来说，如果这个 Project 的 KB 也并大小，经常更新算不算是比较重的操作

**答**：

**不重，因为日常更新是"按 key 的增量 upsert"，成本与 KB 总规模基本无关**。"经常更新很重"对应的是"全量重建"模型，而 Datus 的存储层设计是增量优先的。

### 证据：更新是增量写入，不是重建

**1. 所有领域存储都有按 key 的 `upsert_batch`**（增量语义，`on_column="storage_key"`）：

- `metric/store.py:198`、`reference_sql/store.py:112`、`semantic_model/store.py:447`、`kb_retrieval/store.py:182`
- 更新一个指标 = upsert 一行（主键 `"metric:dau"`）；沉淀一条 SQL Summary = upsert 一行；旧的等义定义还会被去重替换（`metric/store.py:181`）
- 单条写入 LanceDB 是毫秒级，与库已有 1 万还是 100 万条无关

**2. `/build-kb` 是 skill 驱动且增量友好**（`build_kb_commands.py`）：

- "If `AGENTS.md` already exists, **reuse its inventory and only refresh the KB index**"
- 支持 **scope 限定**：`/build-kb orders + order_items tables and queries/*.sql, sales domain only`
- `/bootstrap` 组件级（schema/sql/semantic/metrics/knowledge 分开构建）且中断可续建

**3. 日常沉淀是全自动增量**：`sql_summary` 节点每次查询后自动总结入库、`/session-summarize` 会话沉淀——都不触发重建

### 什么时候确实重

| 场景 | 成本 |
|---|---|
| 首次全量构建大 KB | 重（一次性） |
| **改嵌入模型/维度配置** | **重**——必须全量重嵌入；所以 `check_snapshot` 固定模型快照、`agent.storage.<domain>.model_name` 配置即"不要随便改" |
| FTS 索引重建 / 物化缓存刷新（`refresh_tables/refresh_profiles`） | 中，按需触发 |
| 日常增删改一条知识 | 轻（毫秒级 upsert） |

### 规模上限（对照"几万张表全放进去"）

当前设计**刻意不做**"全库几万张表 + GraphRAG 单一大库"：嵌入式 LanceDB 的舒适区是万级表/百万级 chunk；默认路径是 **project 分片 + scope 限定构建 + schema_linking 选表**——检索时只注入命中的上下文（DRD-03 "prompt 内上下文 vs 检索上下文" tradeoff）。

### 结论

"工程师在同一个 Project 里把知识更新掉" = "改 YAML（进 git）+ 组件级/scope 级重建 or 单条 upsert"——和提交一次代码差不多重；真正昂贵的是"首次全量构建"和"换嵌入模型"，后者用配置稳定化避免。

## Q4：`storage_key` 的 key 到底是什么？

**问**：所有领域存储都有按 key 的 upsert_batch（增量语义，on_column="storage_key"）：key 是什么

**答**：

`storage_key` 的构造规则在 `datus/storage/datasource_scope.py:58`：

```python
def build_storage_key(datasource_id: str, business_id: Any) -> str:
    ...
    if datasource:              # 有数据源
        return f"{datasource}:{row_id}"
    return f"legacy:{row_id}"   # 无数据源的历史行（legacy: 前缀）
```

即 **`storage_key = "{datasource_id}:{业务id}"`** —— 复合键：

| 部分 | 来源 | 例子 |
|---|---|---|
| `datasource_id` | 当前数据源（`resolve_datasource_id`） | `demo` |
| 业务 id | 行记录里的 `id` 字段（`add_datasource_scope_to_rows` 默认 `id_field="id"`） | `metric:dau`、`table:orders` |

实际落库形态：`demo:metric:dau`、`demo:table:orders`；无数据源的老数据是 `legacy:metric:dau`。

### 为什么必须是复合键

**"物理按项目分片、逻辑按数据源隔离"**的直接结果（`datasource_scope.py` 模块 docstring）：

> "Physical storage namespaces remain project-scoped. Datasource isolation is represented by **columns** inside each shared project table."

一个 project 只有**一张** LanceDB 表服务所有数据源，数据源隔离靠表内 `datasource_id` 列。所以唯一键必须把数据源拼进去——否则两个数据源里同名的 `metric:dau` 会互相覆盖。表定义 `unique_columns=["storage_key"]`（如 `metric/store.py:151`）保证唯一，`batch_upsert(on_column="storage_key")` 决定"按这个键更新或插入"。

### 顺带：知识互相冲突的代码级处理

（`metric/store.py:93-105`）：

- **同 key 不同定义 → 抛错不静默覆盖**：`metric_definition_conflict` 逐字段比对核心定义（measure_expr、base_measures 等），新旧都有值且不一致就 raise——防止"同名指标被悄悄改口径"
- **空值视为 unknown 可补全**：legacy 老数据可无痛补全
- **等价定义 → 归并删旧**：`batch_store_metrics`（:177-205）按 metric name 归并，"equivalent definitions are removed in favor of the datasource-local id"，删除陈旧 id 行

**一句话：storage_key = 数据源 : 业务id，是"项目级共享表 + 数据源列级隔离"设计下的唯一键；同 key 下的定义冲突被显式检测（抛错/归并），不会默默漂移。**

## Q5：`extract-knowledge` 的实现逻辑是什么样的？

**问**：`/Users/zhaolipan/hub/Datus-agent/docs/skills/extract_knowledge.zh.md` 对应的实现逻辑是什么样的

**答**：

**`extract-knowledge` 没有 Python 实现——它的"实现"就是 SKILL.md 提示词程序**（v1.3.0），由 Agent 在技能装载机制下按指令执行。

### 执行机制（代码侧）

`触发（/extract-knowledge 或模型自调或其他 skill 编排）` → `skill_manager.load_skill`（`skill_tools/skill_manager.py:147`）→ `registry.load_skill_content` → SKILL.md 全文注入 Agent 上下文 → Agent 按指令执行，可用工具：`execute_sql / task(gen_sql) / read_file / write_file / edit_file / ask_user`。

frontmatter 关键字段：`user_invocable: true`、`disable_model_invocation: false`（**模型可以自主触发**）。

### 编排逻辑（SKILL.md 内部）

**输入解析**（三级优先级）：显式提供（当前消息/附件）→ 从最近对话恢复 `(question, SQL)` 对（**必须 ask_user 确认**，防抓到中间草稿）→ 都没有则 ask_user 索取。

**模式选择**：

- **lite（默认）**：主 Agent 自己"假装不知道答案"模拟草稿 SQL，与 gold_sql 做 diff，从差距里挖知识。零子代理调用、快，但无独立验证
- **deep**：驱动 `gen_sql` 子代理**盲测迭代 ≤5 轮**——只给问题，**绝不泄露 gold_sql 或任何 gold 具体值**；每轮诊断症状（行数多→缺过滤/join；聚合值偏→度量列错…）→ 只描述方向再 hint 重试，**复用同一 session_id**。5 轮未对齐则把已确认的知识缺口入 `### Open Gaps`

**知识挖掘**（Step 5）：

- 4 个轴 diff（表选择/join、过滤条件、粒度聚合、输出形态）+ **系统性语料扫描**（结构性挖常量过滤、术语↔列映射、问法↔列触发映射；阈值事实必带比较符严格性 `> 500` vs `>= 500`）
- 每条候选过 **"worth-writing" 四问**：没有它 LLM 也能答对？能从 INFORMATION_SCHEMA 推断？是通用 SQL 知识？能由已有事实机械组合？——任一为"是"就丢弃
- 产出物是**最短原子事实**（statement 一句话 + 仅在歧义时附最小 SQL 片段）；禁止写 "why it matters"、禁止含问题文本、禁止存 gold SQL

**持久化门禁**（Step 6）：

| 与已有事实的关系 | 处理 |
|---|---|
| 重复（同事实同方向） | 静默跳过（幂等） |
| 精化（旧的是新的子集） | ask_user：替换/合并/带限定共存 |
| **冲突（同范围相反方向）** | **强制 ask_user**，禁止静默解决 |
| 互补（同主题不同侧面） | 追加 |
| 可推导（机械组合） | 丢弃 |

文件布局：`./knowledge/<domain-slug>.md`（**业务域=一个文件**，主题=`##`，≥2 条事实才成主题），优先复用已有域，新建域必须先问用户。

**索引同步**（Step 7）：重写 `./AGENTS.md` 的 `## Knowledge` 段（按域字母序 + `### Open Gaps`）——后续 Agent 从 AGENTS.md 入口就知道该读哪个域文件。

### 触发路径

1. 用户 `/extract-knowledge`（或模型自主加载）
2. **`session-summarize` skill 编排**：把问答对/字段编码事实分类后，轻量项（knowledge 类）以 **lite 模式**喂给它；"one source, two stores"——同一 `(question, gold_sql)` 对既进 reference_sql 存答案形态，又进 extract-knowledge 挖背后的规则
3. `build-kb` / `init` 的生成清单里同样引用（lite 模式，禁止 deep）

### 设计要点

精华是**"盲测子代理"**：gold_sql 不出现在子代理视野里，子代理只能靠问法+schema 猜——它猜错的地方就是通用 Agent 也会踩的坑，正好变成知识；lite 模式用"主 Agent 自我纪律"替代独立验证，换取零成本。这回答的是"知识更新不是改数据，而是从每次成功的分析里挖出可复用的原子规则"，且用冲突门禁防"旧知识互相打架"。

## Q6：一个 skill 就够了吗？不需要对所有涉及的 KB 更新吗？

**问**：工程师做新的 SQL、指标和 Dashboard 时，就在同一个 Project 里面把知识更新掉；这不需要对所有涉及的 kb 进行更新吗？一个 skill 就够了？

**答**：

**不是"一个 skill 就够"，而是"一个编排入口 + 多存储各自写入者"的三层分工**。工程师一次工作会同时牵动多个 KB 存储，但设计上是**分类路由，每个存储只有一个专属写入者**。

### 7 个存储 × 各自的写入机制

（`storage-classify` SKILL.md 的 Decision Tree + Per-Store Reference）

| 存储 | 位置 | 写入机制（唯一） |
|---|---|---|
| knowledge | `knowledge/*.md` | `extract-knowledge`（lite 模式） |
| semantic_models | `subject/semantic_models/{datasource}/{name}.yml` + LanceDB 镜像 | `task(gen_semantic_model)` |
| metrics | LanceDB `metrics` 表 | `task(gen_metrics)` |
| reference_sql | LanceDB | `task(gen_sql_summary)` —— **一条 SQL = 一次调用 = 一行** |
| AGENTS.md | 项目根 | 直接 edit（唯一自己能改的文件） |
| memory | 持久化记忆 | `add_memory` / `edit_memory`（≤2000 字节） |
| skills | 技能库 | `create-skill` |

### 三层分工

```
工程师在 Project 里干活（新 SQL / 指标 / Dashboard）
  → 编排器: session-summarize（收割会话 → 分类 → 出 Manifest → 用户确认）
    → 路由器: storage-classify（决策树：每条产物进哪个存储 + 用哪个机制写）
      → 生成器: gen_sql_summary / gen_semantic_model / gen_metrics
              / extract-knowledge / add_memory / create-skill / 直接编辑 AGENTS.md
```

- **编排入口只要一个**：`session-summarize`（或 `/build-kb`）——工程师视角的"一个动作"
- **但执行是分布式的**：每条产物经 `storage-classify` 决策树路由到**存储专属写入者**——因为每个存储有自己的 schema 校验、向量/FTS 索引、YAML 格式约定
- **单写入者原则（核心设计）**：`storage-classify` 明令"semantic_models/metrics/reference_sql **MUST** go through task subagent，never hand-write their YAML or vector rows"

### 为什么必须这么拆

1. **格式与索引差异**：metrics 是带 `measure_expr`/`metric_type` 的向量行，knowledge 是纯文本原子事实，AGENTS.md 是索引——无法统一写
2. **上下文隔离要求交接**：`task()` 子代理跑在隔离上下文里，路由方必须把 datasource、业务意图、已发现的规则内联成 **prompt-seed** 传下去——"同一 Project 更新知识"靠显式交接成立
3. **一次产物可进多个存储**：同一 `(question, gold_sql)` 对同时路由到 reference_sql（答案形态）和 knowledge（为什么这么写）——"one source, two stores"，**系统自动分发，而不是人工逐个更新**
4. **Two-phase 防失控**：重生成前先出 Summary Manifest 让用户确认（`session-summarize` 硬性回合边界）

### 对照引文

"工程师做新的 SQL、指标和 Dashboard 时，就在同一个 Project 里面把知识更新掉"——准确说是：**产出留在同一 Project 作用域，由 session-summarize 编排、storage-classify 路由，自动分发到对应存储写入者**。单个 skill 解决不了，但"一个编排入口 + 自动路由"让工程师不需要知道该更新哪几个存储。Dashboard 侧走 `gen_dashboard`（BI 平台 CRUD）与 `/bootstrap-bi`（存量资产导入），与知识类存储是两条并行通道。
